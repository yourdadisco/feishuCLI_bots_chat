## 1. 项目概述

### 1.1 项目背景
企业在进行产品决策时，经常需要跨角色协作——产品经理分析市场需求、研发工程师评估技术可行性、总监做最终决策。传统协作流程依赖会议、文档往来，效率低且反馈周期长。

飞书作为企业协作平台，支持机器人应用和事件推送机制，具备构建自动化多 Agent 协作系统的能力。本项目利用飞书开放平台的机器人能力，结合大语言模型（LLM），在飞书群聊中构建一个由**产品总监、产品经理、研发工程师**三个 AI Agent 组成的虚拟产品团队，实现「提出需求 → 自动讨论 → 输出结论」的闭环。

### 1.2 项目目标
1. **即时响应**：用户在群里 @产品总监 提出需求，团队自动启动讨论
2. **多角色协作**：产品经理负责市场/用户分析，研发工程师负责技术评估，总监负责调度和总结
3. **结构化输出**：每轮讨论产出完整的产品分析 + 技术评估 + 综合建议
4. **零人工干预**：从触发到出结论完全自动化

### 1.3 项目范围
- **核心功能**：@触发讨论、多Agent协作、结构化报告输出
- **目标用户**：需要快速获取产品技术决策建议的个人或团队
- **技术栈**：Node.js + DeepSeek API + Feishu Open API
- **部署方式**：Zeabur 云部署 / 本地运行

## 2. 用户画像

### 2.1 主要用户角色

#### 用户A：创业公司产品负责人 (小王)
- **背景**：28岁，某AI创业公司产品负责人，团队仅3人
- **痛点**：
  - 团队没有专职的研发总监，技术决策靠自己判断
  - 做产品方案时要分别找人讨论，沟通成本高
  - 缺乏系统的分析框架，容易遗漏关键角度
- **目标**：
  - 快速获得产品 + 技术的双角度分析
  - 有结构化的结论作为决策参考
  - 减少沟通协调的时间成本

#### 用户B：企业技术管理者 (李总)
- **背景**：45岁，传统企业数字化转型负责人
- **痛点**：
  - 对AI技术了解有限，需要技术专家辅助判断
  - 内部团队对AI方案评估经验不足
  - 需要快速评估外部需求的可行性和成本
- **目标**：
  - 获得易懂的产品分析 + 技术评估
  - 评估外部需求的真实可行性和投入
  - 为决策提供数据支撑

### 2.2 使用场景
1. **产品方案评估**：有了新产品想法，快速获得产品+技术双角度分析
2. **技术选型咨询**：评估不同技术方案的可行性和成本
3. **市场机会分析**：分析新市场方向的用户需求和进入策略
4. **项目可行性判断**：快速判断一个需求是否值得投入资源

## 3. 功能清单

### 3.1 核心功能模块

#### 模块1：群聊消息监听
- **功能描述**：监听群聊中 @产品总监 的消息
- **子功能**：
  1. **事件接收**：通过飞书事件订阅接收 `im.message.receive_v1` 事件
  2. **消息过滤**：只处理群聊中非 bot 的 @消息
  3. **去重处理**：通过 `message_id` 防止重复处理
  4. **多Bot支持**：同一 Webhook 服务处理三个 Bot 的事件推送
- **触发方式**：用户在群里 @产品总监 + 输入需求

#### 模块2：产品经理分析
- **功能描述**：AI 产品经理分析用户需求、市场机会
- **分析维度**：
  1. **用户需求分析**：目标用户的真实需求和痛点
  2. **目标用户画像**：谁会用这个产品，核心场景是什么
  3. **市场机会评估**：市场规模、竞争格局、差异化切入点
  4. **产品建议**：MVP 功能优先级、产品方向建议
- **输出风格**：热情口语化，使用表情符号 🎯

#### 模块3：研发工程师评估
- **功能描述**：AI 研发工程师评估技术可行性
- **评估维度**：
  1. **技术可行性**：是否有成熟的技术方案
  2. **开发周期**：预估 MVP 开发时间
  3. **成本估算**：开发成本、运营成本、API 成本
  4. **技术方案建议**：推荐的技术架构和方案
  5. **风险提示**：潜在的技术瓶颈和风险
- **输出风格**：冷静精准，使用数据，不用表情

#### 模块4：总监调度与总结
- **功能描述**：AI 产品总监调度团队并输出最终结论
- **职责**：
  1. **任务拆解**：将用户需求分解为产品和技术两个维度
  2. **人员指派**：@产品经理 做产品分析，@研发 做技术评估
  3. **阶段性总结**：汇总双方意见，给出综合判断
  4. **最终报告**：输出结构化结论，包括产品建议、技术方案、实施路径

#### 模块5：实时消息推送
- **功能描述**：将团队讨论过程实时推送到飞书群
- **子功能**：
  1. **逐条推送**：每个 Agent 发言独立推送，模拟真实对话
  2. **消息分段**：超长消息自动分段发送（每段2000字）
  3. **@提及**：消息中用 @角色名 明确对话流向
  4. **免打扰**：不 @用户，只在需要时 @对应 Bot

### 3.2 辅助功能模块

#### 模块6：健康检查与监控
- **功能描述**：提供系统健康状态检查
- **实现**：
  - GET 请求返回 `{"status":"ok"}` 健康检查
  - 飞书挑战请求自动响应 `challenge` 验证
  - 日志记录每次事件接收和处理

#### 模块7：环境变量配置
- **功能描述**：通过环境变量管理所有敏感配置
- **配置项**：
  - 三个 Bot 的 App ID / App Secret
  - DeepSeek API Key
  - 飞书群聊 ID

## 4. 非功能需求

### 4.1 性能要求
- **响应速度**：从 @消息到第一条回复 < 10 秒
- **讨论完成**：完整讨论流程 < 60 秒（含 3 秒/轮间隔）
- **事件处理**：事件接收和响应 < 1 秒
- **并发支持**：支持同一群聊顺序处理多个需求

### 4.2 安全性要求
- **密钥隔离**：所有 API Key 通过环境变量配置，不硬编码
- **数据隐私**：用户消息内容不持久化存储
- **权限最小化**：仅使用 `im:message.group_at_msg.include_bot:readonly` 权限
- **HTTPS**：全链路 HTTPS 加密

### 4.3 可用性要求
- **部署方式**：支持 Zeabur 云部署和本地运行
- **错误处理**：LLM 调用失败自动使用预设 fallback 回复
- **服务自愈**：Zeabur 自动重启崩溃的服务
- **日志记录**：每步操作写入日志便于排查

### 4.4 可靠性要求
- **消息去重**：基于 `message_id` 去重，防止重复处理
- **LLM 降级**：API 调用失败时使用预设回复，不中断流程
- **超时保护**：每个 LLM 调用 30 秒超时
- **幂等处理**：相同任务重复触发不重复执行

## 6. 技术约束

### 6.1 必须遵守的约束
1. **LLM API**：使用 DeepSeek Chat 模型（`deepseek-chat`）
2. **API 隔离**：密钥必须通过环境变量配置，不硬编码
3. **飞书 API**：使用 `im.message.receive_v1` 事件接收消息
4. **权限要求**：应用必须有 `im:message.group_at_msg.include_bot:readonly` 权限
5. **消息格式**：文本消息发送，@提及用文字 `@角色名` 表示

### 6.2 建议技术栈
- **运行时**：Node.js 18+（原生 fetch，无外部依赖）
- **Web 服务**：Node.js 原生 `http.createServer`
- **LLM 集成**：DeepSeek API 直接调用
- **飞书集成**：飞书 Open API REST 接口
- **部署平台**：Zeabur（支持 Node.js 自动部署）

## 8. 风险与假设

### 8.1 主要风险
1. **LLM API 不稳定**：DeepSeek API 可能超时或返回异常 → 实现 fallback 回复
2. **飞书事件延迟**：事件推送可能有延迟 → 不影响功能，仅影响响应速度
3. **API Key 泄露**：环境变量管理不当可能泄露 → Zeabur 环境变量加密存储
4. **模型幻觉**：LLM 可能生成不准确的分析 → 多个 Agent 互相校验

### 8.2 关键假设
1. **用户愿意在群里 @机器人触发讨论**
2. **DeepSeek API 能够产出质量合格的行业分析**
3. **飞书事件推送保持稳定可靠**
4. **三个 Bot 的权限配置用户能够独立完成**

## 附录

### A. 术语表
- **Agent**：AI 角色，本项目中的产品总监、产品经理、研发工程师
- **Orchestrator**：调度者角色（产品总监），负责任务分配和总结
- **Webhook**：接收飞书事件推送的 HTTP 端点
- **Event Subscription**：飞书事件订阅机制
- **Challenge**：飞书验证 Webhook 地址时发送的挑战请求

### B. 对话流程示例
```
用户: @产品总监 帮我分析AI客服方案

产品总监: 收到任务。@产品经理 你先做产品分析
产品经理: @产品总监 用户需求是...，市场机会...🎯
产品总监: @研发 你做技术评估
研发:     @产品总监 技术上可行，周期3个月，成本约...
产品总监: 【完整总结】产品分析结论 + 技术评估 + 建议方案
```
